# Optional room activities

Phase 11 source development is owner-authorized while Phase 10 is halted/pending. Phase 10's provider/security evidence and Phase 09's inherited audit gate remain unchanged. This document describes local source behavior, not live deployment or owner acceptance.

`@study/activities` owns the generic ActivityRegistry and the activity runner. Stable SDK ActivityDefinition hooks declare metadata, participant/spectator limits, begin/action/tick/departure rules and viewer-specific projections. Letter Lantern and Sketch Circle register through that same interface. A future definition registers at application composition without editing RoomShell, WorkspaceHost, Presence, Chat, Pomodoro or core realtime. The registry is deliberately a lifecycle/rule interface rather than a game engine.

Applications inject public room-role, social blocking/friendship, identity and occupancy ports. All protected operations use existing HTTP/realtime registries with session/CSRF/Origin/schema/rate checks. The runner serializes per room and rechecks current roles under Rooms' existing transaction locks. Owner-only durable permission configuration supports everyone/moderators/owner/suggestions and independent temporary owner-absent rules. Suggestions-only permits owner launches, with optional local break suggestions; it does not delegate launch permission. A creator manages their offer; current room owners/moderators can cancel or begin. Ordinary users may report current activity content through an activity-owned ephemeral report counter; moderators review the shared canvas/revealed prompts and cancel. Custom drawing packs are owner-only and strictly bounded. Friends-only mode restricts ordinary member projections and admission to the creator's friends. Pairwise blocks deny projections/admission and retire conflicting active participants during maintenance. These controls never reinterpret raw RTC roster entries as social presence.

Lifecycle is lobby → active → transition → active/completed, with cancellation from any unfinished state. Start explicitly joins the creator. Participation is otherwise opt-in: join/decline/spectate/leave. Late arrivals can spectate an active activity; participant admission closes at begin so the server's drawer queue remains predictable. Spectators cannot guess, draw, clear or advance a game. Activity leave never leaves the room. Departing creators transfer management to the next participant; loss of the minimum participant count cancels, and a departing drawer advances through the server transition. An owner leaving the room changes start capability via occupancy but does not transfer permanent room ownership. Empty/closed rooms discard activities; room-role checks deny deleted/removed members immediately. Presence immediately retires a closed socket, so the activity runner retains absent membership for ten seconds while other occupants remain. Absent users cannot act; reconnect restores membership within that grace period. Blocks, role removal and explicit activity leave apply immediately. A fully empty room still discards its activity immediately.

Round deadlines are server timestamps. A one-second maintenance sweep advances expired rounds; a three-second transition reveals the finished prompt/answer before the next round. Reconnect uses the existing authorized snapshot subscription plus a separate clock sample; no client decrement or round-advance action is authoritative. Snapshots use the existing two-second delivery interval and change-only comparison. Drawing delivery therefore has up to roughly two seconds of application latency. No socket, transport switch or permanent stroke persistence is added. A single API process owns each room's ephemeral state, consistent with the accepted room-media limit. Process restart loses activity state and creates fresh activity IDs on subsequent offers.

Commands carry actor-independent room/activity/round/version/request IDs. Identity comes only from the session. Strict schemas reject client score/winner/drawer/turn/role/actor fields. Versions and bounded replay records reject stale commands; per-activity records retain 128 command IDs, and room start histories retain 64 IDs for ten minutes. The runner caps 200 room activities/start histories, 12 participants/12 spectators, 24 encountered identities, five-minute lobby/completed retention, six cooperative word attempts, 20 displayed drawing guesses, three cycles and 30–180-second turns. No persistent leaderboard/economy exists.

Word inputs are bounded ASCII English, case-normalized with bounded surrounding whitespace. Unicode confusables/non-ASCII and invalid lengths fail; dictionary membership is not claimed. Exact matches consume answer letters before misplaced matches, so excess repeated letters receive no credit. The answer remains private until completion/transition; scores come solely from server evaluation. Drawing prompts are private to the current drawer until reveal. Correct guesses are represented as “Correct” so they cannot disclose the prompt to other guessers. The server awards 100 points to a first correct guess and 50 to the drawer; word solving awards `(7 - attempts) × 20` to the solver and 10 to other participants. Scores are ephemeral casual feedback.

Strokes allow four batches of up to 64 finite normalized points, four enumerated ink colors and widths 1–12; unknown fields/tools/pressure fail. The action's serialized JSON is capped at 8KiB within the existing 16KiB ingress envelope. Canvas snapshots cap 40 strokes/512 points and reject overflow; only the active drawer can clear. Guessing allows five accepted actions per ten seconds; drawing allows two accepted batches per second, alongside the operation/ingress/socket limits. The client sends on pointer lift, with local sampling capped at 64 points; no database write occurs per movement. No invalid stroke is committed or broadcast. Bounds apply before trusted rule execution. Snapshot broadcast is authorized per viewer with existing output-buffer safeguards.

`room/activities.ts` registers a compact activity card through WorkspaceHost, a room More/settings launch action, a generic notifications contribution and an independent `mediaMixer` contribution. The SDK's generic `openByDefault=false` prevents optional cards from being opened by initial layout or presentation presets; the explicit action reuses a single card instance. Default placement indexes only default cards, and snap minima include optional types only when targeted or already snapped; registering an unused optional type preserves the existing default geometry. RoomShell hosts generic notifications and honors this generic card metadata, with no concrete game logic/import. Settings contributions refresh on opening so registrations added after preview mount are visible. Native host drag/resize/fullscreen/minimize/popout behavior is retained. Closing the card closes its view; explicit Leave activity leaves participation. Freehand SVG strokes work with pointer/touch input; surrounding controls, guesses and menus use semantic keyboard-accessible controls. Word evaluation uses labels and symbols as well as material styling. Freehand drawing has inherent pointer accessibility limits. No forced motion or modal game mode is introduced.

Pomodoro's public `createBreakObserver` projects its own timestamp state and emits through the shared `timer.break.started` contract/application EventBus. The productivity composition observes account-private/shared snapshots without exposing personal timer state to room transport or replacing panel subscriptions. The activity feature listens only to the public event. First snapshots/reconnect do not manufacture a suggestion. Local preference and dismiss actions control suggestions; no listener starts/joins/opens a game automatically. Normal chat is never parsed as activity protocol.

Activity preferences are version-one account/device records `activities.preferences.<UUID>` in the existing IndexedDB store. They contain only suggestion opt-in, volume and mute (muted by default). SFX uses an injected AudioEffects port backed by the existing ambience engine's AudioContext; short original synthesized tones have independent gains. Unlocking Activity SFX does not enable ambience playback. No new global audio context is created, and the room owner disposes the shared engine. Preferences use existing memory fallback and explicit temporary-storage errors.

Migration `activities/0001_activities` owns only `activities.settings`, a room-keyed durable permission JSON row with room deletion cascade and runtime DML grants. Historical migration files/ledger checksums remain immutable. Settings migration is collected independently of feature enablement. No drawings, scores, guesses, custom packs or round answers persist. Account deletion is handled by current room role/identity checks, occupancy retirement and room cascade; no activity user FK is introduced.

`ACTIVITIES_ENABLED=false` registers no activity routes/realtime handlers/subscriptions/jobs/capabilities. Social disablement also disables activities because validated occupancy/blocking are prerequisites. `NUXT_PUBLIC_ACTIVITIES_ENABLED=false` registers no browser activity owner/card/listener/mixer/suggestion. Configure both for complete rollout disablement. A server-disabled client cannot get an activity snapshot and cannot show a break suggestion. Other room modules keep their existing feature flags. No external dependency, provider token or secret is added.

Deployment implications only: apply the new feature-owned migration using the existing migration role, set rollout switches consistently and retain one authoritative API process per room. API restart cancels ephemeral activities by losing their state. Multi-instance ownership/distribution, faster delta drawing transport, persistent moderation history, arbitrary word packs/third-party corpus imports and later activities need separate design. The owner deploys after review; no Vultr/DNS/OAuth/firewall/live container operation belongs to this phase.
