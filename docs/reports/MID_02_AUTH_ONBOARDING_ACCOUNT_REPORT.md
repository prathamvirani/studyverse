## Delivered experience

The signed-out surface is a focused Study Space glass card with a quiet architectural background, a short heading, locally served original Google/Discord marks, and normal provider buttons. Global navigation is hidden for signed-out and onboarding flows. There is no marketing landing-page expansion. Configured providers have readable names, pending feedback, keyboard controls and recoverable errors. A failed provider start leaves the other provider available; simultaneous attempts are disabled while one flow starts because the existing browser-bound OAuth cookie represents one flow at a time.

`SignIn` checks the authoritative account endpoint before displaying providers. Only a 401 is treated as signed out; connectivity/server failures are not mistaken for anonymous state. The accepted invalid-cookie fallback remains narrowly scoped to public auth discovery/start/finish. Protected operations still reject stale sessions. There is no frontend inspection of HttpOnly credentials.

The account page uses responsive profile, username, provider, appearance/privacy, device and Danger Zone sections. Appearance opens the accepted MID-01 sheet and reuses its theme, width and glass state. Privacy links to the existing Friends controls. Home, room listings, Discover and Friends composition was not redesigned. Existing typography, route readiness/fade, navigation, opaque page cards and room materials remain.

Provider rows expose Connected/Not connected, Link, Reauthenticate and safe Unlink. Unlink requires recent provider verification and locks the account before checking that another **currently configured** sign-in provider remains. Concurrent unlink requests cannot remove the final usable method. Microsoft stays disabled by default; no new provider rollout is implied.

Devices show an editable cosmetic name, OS, browser/version when recoverable, activity time and current-device badge. Raw browser metadata remains inside nested technical details. Windows and reduced macOS user-agent tokens are not presented as trustworthy OS versions; truncated or unfamiliar metadata uses an honest fallback. Existing 120-character server metadata retention remains unchanged. A name never changes session ownership, credentials, trust or revocation. Selected/current, other-device and all-device sign-outs use explicit confirmations.

## Identity and username policy

Permanent opaque UUIDs remain every ownership, membership, friendship and authorization key. Username is a nullable, unique, human-facing handle; display name remains separately editable and non-unique. No existing member is silently assigned a public handle. No public profile, username-resolver, search expansion or DM route was introduced.

- Trim surrounding whitespace, lowercase for storage/comparison, 3–24 ASCII characters, leading letter, then letters/digits/underscores.
- Unicode lookalikes, invisible controls, spaces, punctuation and HTML are rejected. Reserved exact route/provider/system names and staff/product prefixes followed by underscore/digit/end are rejected. The authoritative list is `usernameProblem` in `packages/contracts/src/identity.ts`.
- Availability is authenticated, limited to 60 requests/minute and debounced in the UI. It is advisory; the claim operation rechecks under a per-name transaction lock and a database unique index on `lower(username)`.
- Claims/changes have a 10/minute request budget; a successful change starts a seven-day cooldown. An unchanged name is a no-op. Display-name changes do not consume the username cooldown.
- Client validation provides actionable format/reserved/taken feedback. Server enforcement remains authoritative, including cross-account concurrent claims. Username is never accepted as a principal for ownership or protected operations.
- **Future URL policy:** `/u/<username>` and `/chat/@<username>` would resolve the current owner at request time, then use the UUID internally. A released old name has no permanent alias or redirect: it is immediately claimable, unresolved names return not found, and re-claimed names belong to their new owner. Future links must never promise immutable identity from a handle. No alias table was justified for MID-02.

These are basic abuse controls, not a claim to provide comprehensive moderation or stop every ASCII impersonation.

## Routing and onboarding coordinator

`/home` is the preferred navigation and successful-login destination. The existing index page has a `/home` alias, preserving `/` compatibility without duplicating Home composition. Explicit account reauthentication returns to `/account`; dedicated deletion verification returns to `/account#delete`.

A shared internal allowlist accepts Home, Account, My Rooms, Discover, Friends, room paths and bounded invitation fragments. External/protocol-relative URLs, encoded separators, callback loops and arbitrary return query parameters fail validation. The server stores the return destination in the existing browser-bound OAuth flow. Incomplete onboarding stores its validated destination in the account row, survives a reload and clears it to `/home` on completion. An invitation bearer is never written to localStorage/sessionStorage. Invite authorization still occurs at acceptance; merely returning to the route grants no room access.

`identity.users.onboarding` holds `{version:1, identity, appearance, layout}`. Required identity setup and recommended presentation milestones are centrally coordinated from authoritative profile state in the shell, with `/account` retained as a security/recovery escape. Each server update locks the user and merges only its milestone; layout requires appearance, appearance requires identity. Closing a tab resumes the first incomplete milestone. Appearance/width values themselves continue using MID-01's device-local preferences and validated SSR mirrors, not a second server preference implementation.

Fresh signups choose display name and live-checked username, then System/Light/Dark previews, then Auto/Compressed/Full-width previews. Displays at least 1800px wide with aspect ratio above 20:9 get integrated animated width previews; reduced motion disables animation. No second ultrawide modal appears. Existing rows are backfilled with appearance/layout already complete, so they choose only identity/username and keep their prior device settings.

Notifications, calendar, passkeys, microphone, camera and native-app prompts remain contextual and unimplemented here. There is no speculative optional-defaults step. Future schema versions must migrate/merge existing milestone completion explicitly, update the contract and preserve prior choices; the strict v1 contract intentionally rejects unknown versions today.

No production backup/retention policy is invented here.

## Account deletion policy

The Danger Zone explains consequences before OAuth. A dedicated reauthentication flow must return the same existing provider identity for the same account and session. Only that explicit flow produces a server-held five-minute deletion proof. Normal sign-in, ordinary reauthentication, frontend flags, another session, wrong provider identity and expired proofs cannot authorize deletion. The user then types exact uppercase `DELETE` and chooses the final destructive button. This is OAuth step-up, **not two-factor authentication**; providers retain their own account-selection/consent behavior.

Deletion atomically consumes the proof, deletes the account and cascading owned records, and erases every subject session, including expired/revoked rows and browser metadata. A shared subject lock serializes OAuth session issuance with erasure and rechecks that the user still exists, preventing a concurrent login from leaving an orphan/live session. Confirmation accepts no target user ID: authorization comes only from the server actor. Browser session/flow cookies and in-memory CSRF state are cleared after confirmed erasure.

| Personal tasks/timers       | Delete subject-owned records.                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Invitations                 | Delete invitations for deleted rooms and invitations sent by/to the account.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Friendships/blocks/privacy  | Delete all account-owned or account-referencing rows.                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Provider identities/profile | Delete; a future signup is a new UUID/account. No recoverable public tombstone or username reservation.                                                                                                                                                                                                                                                                                                                                                                                                     |

Deletion lifecycle subscriptions are explicitly enabled in the full API composition; standalone feature harnesses can omit identity without registering an unknown event. The EventBus bounds subscribers and records failures. Durable erasure/session denial does not depend on a successful UI cleanup or synchronous media provider availability. Existing single-process event/lease limits remain; this work does not claim a distributed erasure bus.

## Security and preservation

HttpOnly/Secure/SameSite cookies, request Origin/CSRF validation, OAuth state/nonce/PKCE, issuer/subject ownership, current-session binding, refresh rotation and stale-session rejection remain on their accepted paths. New commands use strict schemas, actor-scoped resources, rate limits and transaction boundaries. Device rename cannot rewrite raw metadata or target another user's session. Unlink cannot remove the last configured method. Account deletion needs its own server proof even when a login is already recent. Return URLs are validated both when accepted and consumed. No auth token moves into browser-readable persistence.

## Google One Tap / FedCM decision

**Deferred.** The accepted integration is authorization-code OAuth with PKCE and server-side exchange; it does not have a Google Identity Services credential verification/nonce endpoint, One Tap lifecycle coordinator or an approved script/CSP integration. Adding a parallel credential path solely for this visual phase would broaden the authentication architecture. The normal branded Google/Discord buttons remain authoritative and fully available. Future work needs a separately reviewed GIS credential flow, server session eligibility check, provider/browser dismissal and cooldown handling, failure isolation, CSP/privacy review and browser coverage. No pretend One Tap UI or frontend cookie heuristic was added.

## Limitations and deferred scope

Validation is local Chromium with emulated desktop/tablet/mobile, OS theme and reduced-motion preferences; physical mobile, Safari/Firefox and screen-reader certification are not claimed. OS/browser descriptions are intentionally approximate when user agents are reduced/truncated. Account erasure cannot reach another device's local files or rewrite previously delivered/cached content. Basic username policy does not replace future moderation. OAuth step-up verifies provider control without claiming an extra factor or forcing a password challenge unsupported by the provider.

MID-03 Home/Rooms/Discover/Friends composition, MID-04 room/presence/privacy redesign, later productivity/media refreshes, full profiles/DMs, alias infrastructure, advanced device fingerprinting, passkeys/2FA, distributed account erasure, marketing landing page and One Tap/FedCM remain deferred. Known pre-existing external YouTube/two-client loop limitations were not declared fixed. **Stop after MID-02; Phase 09 and MID-03+ remain unstarted.**
