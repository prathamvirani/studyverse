## Duplicated and problematic patterns

### Shell, heroes, search and cards

Five hero usages: `pages/index.vue:27`, `pages/friends.vue:65`, `pages/invite.vue:30`, `pages/auth/callback/[provider].vue:32`, `pages/rooms/[id].vue:204` (all below `apps/web/app`). The shared `.hero` in `app.vue:174` applies a pale block, 24px radius, large padding and oversized global serif heading. Home, Friends and management particularly spend useful screen space on this repeated composition. Account, Create, My Rooms and Discover have oversized heading treatment but **do not** use `.hero`; distinguish the two findings.

The duplicated pattern is page composition and styling, not multiple shell files. `.heading-row`, `.card`, `.form`, `.actions` and one-column stacks recur across routes. The adaptive grid itself uses `auto-fill/minmax(280px)`; the global width cap limits desktop density and Home additionally slices to three records. There is no explicit three-column CSS cap. The 3440px capture demonstrates the large unused margins.

`RoomListing.vue:45` is the only current search form. It serves both list routes with the same fixed `search` ID, maximum 500px width and detached Search button. Background categories are filters, while task/chat/media composers are commands, not duplicate searches. There are no current Friends, chat-history, member/invite or settings search fields to consolidate. A future context pane rendering multiple listings would need unique field IDs and independent query/cursor state.

`RoomCards.vue:7` and room details independently format privacy/count/identity. Cards correctly pluralize members, while details says “1 members.” Badges expose lowercase enum values. Friend activity and invite rows are contextual room links, not competing complete RoomCard implementations. Extract a single card from the existing renderer instead of replacing several imagined duplicates. Direct entry must preserve POST join and late-navigation cleanup; settings actions must never trigger entry.

## Architectural constraints and risk register

1. **Dependency direction:** core/SDK/UI remain feature-neutral; room features register named contributions and tile definitions. LiveKit and YouTube stay in adapters. No indirect feature imports through RoomShell helpers, cycles, production test imports or SQL ownership bypasses. Keep semantic filenames and migration owners/order/checksums.
2. **Security and data:** keep HttpOnly server sessions, CSRF/Origin, strict versioned schemas, IDOR/BOLA defenses, current membership/blocks/roles, rate limits and separate Personal/Shared data. UI visibility never authorizes an action. Existing GET/query paths must not become join/save operations when cards or routes change.
3. **Presence report versus privacy:** Reference Context §75 reports two Google users able to chat but only one visible. This was not reproduced with the real accounts in MID-00. Accepted presence defaults deliberately hide current room from others' rails; explicit Offline and blocks further affect projection. Existing two-client social tests opt both users into room visibility. MID-04 must reproduce both opt-in and hidden cases, check join/reconnect/rendering, and keep chat delivery intact. Never publish private RoomOccupancy identities or raw SFU roster to “fix” the rail. Changing accepted privacy semantics requires an explicit owner decision.
4. **RTC invariants:** no capture on entry or automatic retry after device denial; no duplicated camera renderer; preserve opaque receive-only identities, per-connection leases, grant revocation/inventory cleanup, publisher projection and requested-versus-actual diagnostics. UI restyling cannot raise deployment tiers or claim hard SFU RTP caps. Single API/process and outage bounds remain.
5. **Room geometry:** keep background dominance, participants left, canonical Media/Background/Mic/Camera/Share/More order, existing productivity order until its authorized modular evolution, keyboard drag/resize, focus escape and local preference recovery. Preserve `demo.sandbox` and persisted geometry. Avoid route animation keeping two active room trees/capture sessions alive.
6. **Media authority:** HTTPS/WebSocket carry control state; provider streams remain direct. Preserve owner baseline, temporary non-owner/FFA overrides, owner keep/restore/review, private occupancy-driven empty reset, epochs/versions and local/shared mix separation. A hidden visible tile must not issue an unauthorized shared pause/play.
7. **YouTube reliability and policy tension:** Reference Context §103 reports a ~2s loop until Resume. Current local iframe controls can fight authoritative paused state; code review supports that hypothesis, not a confirmed reproduction. MID-06 needs a real two-client one-action regression in addition to mocks. Accepted ROOM_MEDIA architecture currently requires a visible embed and pauses/destroys local playback when hidden/minimized/closed. The later audio-first/optional-video request is conditional on technical/provider constraints: revalidate those before changing lifecycle; do not assume hiding an iframe or extracting audio is an approved solution. Metadata APIs, CSP and safe thumbnail handling require deliberate review then.
8. **Immediate save:** timer configuration currently requires a paused timer; quality reapply can renegotiate publication; media commands carry revision preconditions. Debounce/coalesce with error/conflict feedback, preserve last accepted state and do not emit a command per animation frame. Ordinary UI polish must not change these contracts.
